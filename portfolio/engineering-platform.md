# Платформа для инженеров-проектировщиков

> **Коротко.** SaaS из четырёх сервисов для проектирования электротехнических систем: каталог из ~1,5 млн изделий, конструктор логических моделей с версионностью и инженерное рабочее место на графовой БД.
> Я был ведущим backend-разработчиком и архитектором: выбрал стек, спроектировал архитектуру и схемы данных, руководил двумя разработчиками и сам писал код. Проект доведён с нуля до релиза, им пользуются крупные компании.

## Контекст

Инженеры, которые проектируют электрошкафы и распределительные щиты, работают в связке «выбрать изделие → разместить → подключить → выпустить документацию».
Данные об изделиях лежат у производителей в разном виде, логику проекта приходится каждый раз собирать вручную, а серийные номера и подбор аналогов делаются по памяти и таблицам.

Платформа закрывает эту цепочку целиком: есть общий каталог изделий, система описания логики и рабочее место, где всё это собирается в проект.

## Архитектура

Четыре сервиса связаны между собой: единая авторизация, две «поставляющие» системы (логика и данные) и инженерное рабочее место, которое их объединяет.

**ID** — единая точка входа. Администратор организации управляет пользователями и подпиской.

**DP (портал данных)** — аналог маркетплейса для инженерных изделий. Пользователь находит изделие (например, автоматический выключатель), смотрит характеристики и принадлежности, скачивает архив `.edz` для импорта в EPLAN или `.7z`. В архиве лежит всё: схемы сверления, общие данные (`partxml`), 2D- и 3D-макросы, схемы установки, документация.

**ISM** — система логической сборки. Здесь описывается, из чего состоит изделие или шкаф: какие классы, какие в них входят элементы, какие у них свойства и связи, формат серийного номера. Всё это живёт внутри моделей, у каждой модели есть версии.

**PBS** — рабочее место инженера в вебе и на десктопе (поэтому Node.js). Инженер берёт логику из ISM и конкретные изделия из DP, расставляет серийные номера, подбирает аналоги и выпускает техническую документацию через генератор документов.

**Плагин для EPLAN (C#)** — встраивает страницу портала данных прямо в окно EPLAN. Пользователь работает как в браузере, а при скачивании плагин перехватывает ссылку, забирает архив и запускает импорт.

## Сквозной сценарий

1. Администратор организации заводит пользователей в **ID**.
2. Разработчик стандартов описывает в **ISM** модель шкафа: классы, свойства, связи и шаблоны серийных номеров. Каждое изменение попадает в версию модели.
3. Инженер в **PBS** берёт модель, подбирает конкретные изделия из **DP**, проставляет значения свойств и размещает элементы.
4. Платформа генерирует серийные номера по шаблонам, предлагает аналоги там, где нужной позиции нет, и выпускает техническую документацию.
5. Нужные изделия подтягиваются в EPLAN из DP с помощью плагина.

## Решения и результаты

### 1. Парсер архивов `.edz`: отказоустойчивость на «неидеальных» данных

**Проблема.** Архивы приходят из разных источников (S3, Яндекс.Диск, API), и почти каждый уникален. Один архив может содержать одно изделие с тяжёлым 3D-макросом (~5 ГБ), другой, другой — десятки изделий, у которых есть только XML.
На первых тестовых архивах не хватало полей, потом появились пользовательские поля и схемы сверления, у одного производителя в XML встретилась кириллица, а принадлежности у разных производителей описаны по-разному.

**Решение.** Парсер разработан в несколько итераций: каждая новая нестандартная ситуация закрывалась обработкой и тестовым кейсом. Главной целью была максимальная отказоустойчивость, чтобы один «странный» архив не ломал загрузку всего остального. Каждый шаг парсера детально логируется и доступен через Log Viewer.

**Результат.** В каталоге ~1,5 млн изделий, объём хранилища ~20 ТБ. Новые форматы данных разбираются с понятными логами вместо молчаливых сбоев.

### 2. Серийные номера и подбор аналогов на графе

**Проблема.** Серийный номер собирается из частей: счётчика, разделителей, номера родительской позиции и значений свойств (цвет, код страны и т. д.). Если шаблон меняется у одного класса, он должен поменяться у всех наследников. Аналогичная задача с подбором аналога: нужно найти изделие, максимально похожее по свойствам.

**Решение.** Иерархию классов и связи со свойствами я хранил в **Neo4j**.
- *Серийные номера.* Шаблон задаётся классу и хранит порядок частей. Счётчики проставляются автоматически, значения наследуются от родителей, разделитель всегда статичный, а значения свойств берутся из того, что выбрал инженер. Когда шаблон меняется, граф сразу выдаёт всех наследников, и не нужно рекурсивно считать дерево в SQL.
- *Аналоги.* Берём класс и его связи и смотрим по графу, у кого больше всего таких же связей: те же свойства с теми же значениями. Например, у двери есть высота, ширина и материал. Если у соседней ноды совпадают эти значения, она встанет на место прежней.

**Результат.** Поиск потомков и аналогов превращается в обход графа вместо рекурсивных запросов и ручного слияния свойств.

### 3. Версионирование моделей

**Проблема.** У каждой модели несколько версий, нужно показывать состояние на любую версию и историю изменений любой сущности.

**Решение.** Все изменения внутри модели складываются в таблицу `model_version_relation`: полиморфная ссылка на сущность, JSON с изменениями, id модели и id версии. Чтобы показать версию N, backend собирает состояние сущности из всех записей до этой версии включительно. Версию 3 мы получаем по записям версий 1–3, версию 2 — по записям до третьей. История изменений сущности строится из тех же данных.

**Результат.** Нет дублирования данных между версиями, вся история и просмотр любых версий работают на одном механизме.

### 4. GraphQL вместо REST

**Проблема.** Для экрана модели нужно за один раз получить список недавних моделей, дерево классов, аспекты, свойства, версии и так далее. Через REST пришлось бы делать много мелких запросов.

**Решение.** Во всех сервисах платформы API с самого начала проектировали на GraphQL (на PHP-сервисах — Lighthouse), в едином стиле: фронт запрашивает только нужные поля и получает несколько сущностей одним запросом. В табличных экранах пользователь сам выбирает отображаемые поля и размер пагинации, и GraphQL здесь подходит естественно.

**Проблема N+1** обычно решается директивами со связями, но они не дали отрисовать версионность. Поэтому я написал отдельные резолверы и собственные директивы.

**Результат.** Меньше сетевых запросов с фронта и гибкость в таблицах, версии при этом отображаются корректно.

### 5. Работа с большими объёмами

**Проблема.** Когда данных становится много, всё начинает тормозить: крупный импорт, огромное дерево классов, большое количество индексов свойств.

**Решение.** Оптимизации сделал точечно:
- Индексы свойств перестали хранить в БД. Остался только общий счётчик. При проставлении значений хранится только само значение, пустые остаются пустыми.
- Дерево классов отдаётся облегчённым: только название, категория, `id` и `id` родителя вместо полностью отрисованного дерева.
- Импорт в несколько аспектов оптимизирован по максимуму и в БД, и в коде. На фронте добавлены поэтапные лоадеры: «классы — 90%, теперь свойства — 15%» и так далее.
- Долгие операции (импорт, скачивание изделий, клонирование модели) работают в фоне, а прогресс приходит на фронт в реальном времени через Socket.io, поэтому пользователь продолжает работать, пока они выполняются.

**Результат.** Крупные импорты и деревья перестали блокировать работу, а пользователь видит, на каком этапе загрузка.

## Качество и эксплуатация

- **Тесты:** TDD, 90% покрытие backend-кода, E2E-сценарии на Playwright, нагрузочное тестирование на Apache JMeter.
- **Статический анализ:** PHPStan без ошибок, форматирование через Pint.
- **CI/CD:** GitLab, Docker для локальной разработки и развёртывания. Первичное код-ревью делает ИИ-агент, затем ручное ревью.
- **Мониторинг:** Sentry, Telescope и Horizon, Log Viewer для детального просмотра логов.

## Точки роста

- Пользователей пока немного, поэтому реальной боевой нагрузки платформа ещё не видела. Узкие места я нашёл на больших объёмах данных и на нагрузочных тестах, но их поведение на живом трафике мне ещё предстоит увидеть.
- Парсер архивов остаётся зависимым от новых форматов производителей: каждый новый источник данных может потребовать доработки.
